# Single primary Python SDK migration

## Identity and breaking changes

The one maintained SDK is licenx at SDK/client/python/licenx. The former
reference package x_license_python has been removed from active source and
release workflows. Existing applications importing x_license_python must
migrate explicitly; this is a breaking change. Historical audit Markdown
may retain references as recorded evidence.

## Install and config

Use `python -m pip install ./SDK/client/python/licenx` from a trusted checkout.
The Admin download endpoint `GET /api/sdk/download/python` now serves
`licenx-python-sdk.zip`, whose extracted directory supports `pip install .`.
A vetted wheel from a separately authorized GitHub Release is also supported.
Public `pip install licenx` must NOT be trusted until PyPI name ownership,
package integrity, versions, signing and release have been verified.
No PyPI upload, tag push, or release asset publication was authorized here.

Create application-root `licenx.config.py` with a literal `app_config` dict.
The SDK uses AST literal parsing, not arbitrary Python execution. Include the
actual client app_version, valid HTTPS server_url, app slug and known trusted
public_key_pem. No private signing key, customer license, token or password
belongs in the config. An editable Python config is not a security boundary;
production apps should independently pin trusted endpoint and public key
fingerprint or verify cryptographically signed key rotation.

## Release guardrails

Source ZIP excludes test directories, Python caches, egg-info, private data
and symlinks. The parity verifier ensures byte-for-byte source agreement.
Node, Cloudflare and Docker use the same primary ZIP name. GitHub SDK tag
workflow checks pyproject.toml as the single SDK version source, tests only
the maintained package, builds wheel+sdist, and verifies checksum assets.
Before a new authorized release, choose a fresh SDK version and tag rather
than overwriting an existing version. Test pip installation from the built
wheel in a clean venv and validate signature/nonce/WSS/HTTP regressions.

## No production action

This is a source/CI migration, not a VPS deployment or Admin WSS activation.
CalGrid prior standalone EXE bundles remain historical binaries until a new
separately approved Windows build and controlled PC/RDP login retest.

## PyPI publication via GitHub repository secret

The GitHub Actions workflow `.github/workflows/release-python-sdk.yml` now
publishes the primary `licenx` wheel and sdist to PyPI using the repository
Actions secret named **`PYPI_API_TOKEN`**. It does NOT publish on ordinary
pushes, PRs, or GitHub Releases generated by unrelated actions. The existing
release workflow is triggered by an explicitly created `python-sdk-vX.Y.Z`
tag; after version/main-ancestry checks, platform SDK tests, packaging,
GitHub Release upload and checksum verification, a separate low-permission
`publish-pypi` job downloads the verified distributions and runs
`pypa/gh-action-pypi-publish@release/v1` with `user: __token__` and the secret.

To run a new release after merging and reviewing PR #1:

1. Confirm the targeted package name and PyPI account ownership. For a first
   upload to a previously nonexistent PyPI project, the API token must be
   permitted to create that project; a token scoped to an uncreated project
   will not authenticate. Never paste the token into issues, logs, or chat.
2. Choose a **new** version not already published on PyPI; update
   `SDK/client/python/licenx/pyproject.toml`, run the reviewed CI and merge
   that version change. Public PyPI versions and filenames cannot be overwritten.
3. Create and push an annotated tag `python-sdk-vX.Y.Z` pointing to the
   reviewed **main-branch commit** with precisely matching `pyproject.toml`
   version. The tag push (not the `release.published` event) is authoritative
   because the existing workflow itself creates a GitHub Release using
   `GITHUB_TOKEN`; such generated events do not reliably start another workflow.
4. Watch all matrix SDK tests, wheel/sdist build, GitHub Release asset
   checksum checks, and the final `publish-pypi` job. PyPI succeeds only
   after the final job reports success, then verify the files on PyPI and
   run `python -m pip install licenx==X.Y.Z` in a clean environment.

`python -m build` creates a standard, **pure-Python wheel and sdist**, not a
Nuitka/Cython native compiled or tamper-resistant SDK. Binary compilation
and platform-specific wheels would require a separate audited design and CI.
The token is not used during code builds, not printed, and is only passed
to the isolated publishing job. If a tag has already been uploaded, reruns
will fail rather than silently skip or overwrite an immutable PyPI version.

## Explicit SDK release request (GitHub Actions permission-safe trigger)

Because this GitHub integration cannot create tag refs directly, the controlled
release path is an explicit new file committed to `main`:
`SDK/release-requests/python-sdk-vX.Y.Z.txt` containing exactly two lines:

```text
version=X.Y.Z
source_sha=<reviewed previous main commit SHA>
```

The `Authorize an explicit SDK release request` GitHub workflow accepts only
a commit adding exactly one new release-request file, validates that its
previous commit and the `licenx` package version match, and uses a minimal
`contents:write/actions:write` GitHub Actions job to create the immutable
`python-sdk-vX.Y.Z` tag. It then explicitly dispatches the existing
`release-python-sdk.yml` on that exact tag, because GitHub suppresses
ordinary push events for tags created using `GITHUB_TOKEN`. The existing
tag workflow runs full platform SDK tests, source/wheel checks, GitHub Release
checksum verification and the separately permission-scoped PyPI upload job.

**No release request file is added by merging this documentation alone.**
Only an independently approved release-request commit can trigger a publish.
After publication, do not delete or edit a release request to rerun a release;
PyPI package versions and filenames are immutable. Do not put secrets in the
request file.
